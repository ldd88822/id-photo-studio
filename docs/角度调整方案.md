## 一、需求与边界

### 1.1 要解决的问题

用户上传的照片往往不是「正对镜头、水平端正」的：

| 常见问题 | 成因 | 需要的能力 |
|---|---|---|
| 仰拍 / 俯拍 | 手机举高或放低 | 俯仰纠正（Pitch） |
| 整幅画面歪斜 | 手机没拿平 | 自由旋转（Rotate） |
| 横竖方向弄反 | 扫描件 / 自拍镜像 | 左右镜像（Mirror） |
| 靠近拍导致脸变形 | 手机广角镜头 | 镜头畸变校正（Distort） |
| 旋转后边角留白 | 旋转的必然结果 | 画面缩放（Zoom） |

> v1.2 起，「歪头 / 侧脸」不再单设参数 —— 实际使用中这两个场景用**画面旋转**
> 就足以处理证件照的需求，单独立项反而增加理解成本。

### 1.2 设计边界

- **只做几何校正，不做人脸重绘**。不生成不存在的像素，只对已有像素重采样。
- **本地计算，零上传**。所有变换在浏览器 Canvas 上完成，照片不出本机。
- **不阻断主流程**。角度功能默认关闭，用户不开启时保持原有的平移 / 缩放手感。
- **参数可回滚**。任何调整都能撤销，也能一键回到原图。

## 二、可调整参数

### 2.1 参数表

| 参数 | UI 名称 | 范围 | 步进 | 默认 | 含义 |
|---|---|---|---|---|---|
| `rotate` | 自由旋转 | −90° ~ +90° | 0.1° | 0 | 整幅画面绕旋转中心在平面内旋转，用于摆正歪斜的照片 |
| `pitch` | 俯仰（Pitch） | −25° ~ +25° | 0.1° | 0 | 绕水平轴（X 轴）旋转，纠正仰拍 / 俯拍 |
| `zoom` | 画面缩放 | 0.5 ~ 2.0 | 0.005 | 1.0 | 补偿旋转造成的边角留白 |
| `distort` | 镜头畸变 | −0.3 ~ +0.3 | 0.005 | 0 | 桶形（>0）/ 枕形（<0）畸变校正，作用在整幅成品上 |
| `fov` | 镜头距离 | 0.8 ~ 4.0 | 0.05 | 1.8 | 虚拟相机距离，越小透视越强（仅 3D 旋转时生效） |

**布尔开关（不在 `ANGLE_PARAMS` 里，单独用 `ANGLE_FLAGS` 声明）：**

| 参数 | UI 名称 | 默认 | 含义 |
|---|---|---|---|
| `mirror` | 左右镜像翻转 | false | 沿画布中垂线把照片翻面，用于纠正左右颠倒 |

之所以拆成两张表：开关没有 `min`/`max`/`step`，滑块渲染逻辑套不上。硬塞进同一张表会让
「参数表驱动 UI」这条路反而变绕 —— 不如显式分成「数值参数」与「布尔开关」两族。

### 2.2 范围与精度的取舍理由

**旋转类参数步进 0.1°** —— 证件照对「端正」的判定是肉眼级的，0.1° 的差异人眼不可辨；再细没有意义，再粗会出现「差一点点摆不正」的挫败感。

范围取 ±90°（rotate）/ ±25°（pitch）：

- `rotate` 放到 ±90° 是为了支持**横竖对调**（拍歪 90° 的照片、需要转正 90° 的扫描件）。
  90° 是个天然的对称点 —— 左右边界互为镜像、不存在「转过去一点」的中间态，
  是「自由旋转」这一命名能够成立的上限。再大（如 180°）等价于镜像 + 旋转组合，
  用户可以自己拼出来，不必单设。
- 3D 旋转（pitch）仍限制在 ±25°：超过这个角度后，投影拉伸导致的边缘模糊会明显可见，
  属于「救不回来」的范畴。

**`distort` 与 `fov` 默认隐藏细节** —— 这两个是进阶参数，普通用户不需要懂；滑块照常显示，但放在参数列表末尾，不抢视觉重心。

### 2.3 参数分组

```js
const GROUPS = {
  rotate: ['rotate', 'mirror'], // 自由旋转 + 镜像（都属「摆正照片朝向」）
  pitch:  ['pitch'],            // 俯仰纠正
};
```

镜像归到 `rotate` 组，是因为它和旋转同属「摆正照片朝向」这一类操作 ——
用户点了「复位本组」时，期望的是「把朝向恢复原样」，把镜像留在原地会显得莫名其妙。

分组的作用有二：① 「复位本组」按钮只清当前模式相关的参数，不会误伤其他维度；② 切换模式时，无关滑块自动变暗（`.dim`），减少视觉噪音。

## 三、交互方式

### 3.1 五条并行通道

用户可以用任意一条或几条混合操作，所有通道共享同一份 `params` 状态，实时双向同步。

| # | 通道 | 交互 | 适用场景 |
|---|---|---|---|
| 1 | **快捷模式** | 顶部 2 个按钮切换当前操作维度 | 明确的单项纠正 |
| 2 | **滑块** | 拖动 range，实时生效 | 精细微调，能看到数值变化 |
| 3 | **数值输入** | 直接键入数字，回车或失焦生效 | 精确复现某个值 |
| 4 | **画布拖拽** | 直接在照片上拖 | 所见即所得，最直观 |
| 5 | **键盘方向键** | ←→ 调水平类，↑↓ 调俯仰类 | 逐格微调，手不离键盘 |

### 3.2 拖拽灵敏度

拖拽位移按画布尺寸归一化（`dx = Δx / 画布宽`），因此在不同屏幕上手感一致。

```js
const SENS = { rotate: 60, pitch: 28 };
```

含义：拖满整幅画布宽度（`dx = 1`）对应的参数变化量。

`rotate: 60` 是权衡后的取值：量程放开到 ±90° 后，若沿用 42，拖满一次只能覆盖不到一半量程，
用户要拖两三次才到端点；若提到 90，又会让小角度调整过于敏感（拖 10px 就转 6°）。
60 意味着**拖满约 1.5 个画布宽可达 ±90° 端点** —— 小幅摆正仍在一拖之内，
大幅度翻转也不必反复拖拽。

- **rotate**：水平拖动，左拖逆时针、右拖顺时针。
- **pitch**：垂直拖动，**上拖低头、下拖抬头**（`pitch -= dy * SENS.pitch`，`dy` 向下为正，所以下拖增大 pitch，符合「把画面往下拉＝把下巴压下来」的直觉）。

### 3.3 旋转中心选择

| 选项 | 行为 |
|---|---|
| **画面中心** | 默认。绕输出画布几何中心旋转，适合整幅摆正 |
| **人脸中心** | 用检测到的人脸框中心作为轴心，适合只纠正头部 |
| **自定义** | 拖动画布上的橙色十字标记移动轴心，用于特殊构图 |

实现要点：

1. **旋转中心只作用于几何链，不影响底图铺排。** `cover` 恒定以画布为中心基准（透视梯形同理），否则会出现「换了轴心，人像整体跑偏」的怪异现象。测试 `[6b] 旋转中心` 与端到端「透视与轴心解耦」用例显式守住了这条。
2. **轴心靠拖拽移动，不靠点击定位。** 早期版本在 `pointerdown` 时无条件把点击位置设为轴心，导致用户每做一次旋转就被悄悄改掉轴心。现在改为：只有按住橙色标记附近（`hitPivot()` 命中，容差 `max(14, w*0.1)`）才开始移动轴心，普通拖拽一律是旋转。
3. **轴心标记要够醒目。** 半径取 `max(10, 画布宽 * 0.075)`，加深色描边保证浅色背景上也能看清，并附「旋转中心」文字标签。

### 3.4 辅助视觉

- **水平自动吸附**：`rotate` 在 ±2° 范围内自动归零，避免留下「看得出来的 1.5° 歪斜」。可关闭。
- **三分构图网格**：叠一层 3×3 网格，用「眼睛在水平中线附近、头部居中」的经典构图规则做视觉参照。
- **旋转中心标记**：非画面中心时，用橙色十字圆环标出轴心位置。
- **实时联动**：任何参数变化立即重绘主画布 + 触发三底色缩略图重渲染，所见即所得。

## 四、撤销 / 重做机制

### 4.1 状态快照栈

只存**参数对象**（约 200 字节），**不存图像数据**，因此 80 步历史的内存占用可以忽略。

```js
class History {
  stack = [];   // [{ state, label, time }]
  index = -1;   // 当前指针位置
  limit = 80;   // 环形上限，超出则 shift 掉最老的
}
```

### 4.2 三类操作

| 方法 | 场景 | 行为 |
|---|---|---|
| `reset(state, label)` | 上传完成 / 回到原图 | 清空栈，把当前状态作为不可再撤销的栈底 |
| `commit(state, label, merge)` | 每次参数变更 | 压入新快照；`merge=true` 时可能合并进栈顶 |
| `seal()` | 松手 / 失焦 | 打断合并窗口，下一次变更必定产生新快照 |

### 4.3 合并策略（关键设计）

拖动一个滑块会连续触发几十次 `input` 事件。如果每次都压栈，用户按一次撤销只能退回 0.1°，体验灾难。

合并条件（三者同时满足才合并）：

1. `merge === true`；
2. **标签相同**（都是「水平旋转」，不会把旋转和缩放并成一条）；
3. **距上次提交 < 500ms**；
4. **指针位于栈顶**（撤销后再改，不能覆盖已被回退的那些步骤）。

合并时用新快照**替换**栈顶而非新增，所以「拖一次滑块 = 一条历史」。

`pointerup` / `change` / `seal()` 会重置时间窗口，保证「拖一次、松手、再拖一次」是两条独立历史。

### 4.4 撤销时的分支处理

在撤销到某一步之后再改参数，指针之后的「未来」会被截断丢弃（`stack.length = index + 1`），这是标准的线性历史语义，避免出现分叉。

### 4.5 三档复位

| 按钮 | 作用范围 | 是否可撤销 |
|---|---|---|
| **复位本组** | 只清当前模式相关的参数（如处于 `pitch` 模式则只清 `pitch`） | 是，压入一条「复位本组」 |
| **全部复位** | 清空所有角度参数 | 是，压入一条「全部复位」 |
| **回到原图** | 清空参数 **且** 清空历史，栈底重设 | 否，属于明确的「重开」操作 |

### 4.6 参数导出 / 导入

- **导出参数**：把当前参数 + 源图尺寸 + 输出尺寸写成一个 `角度参数.json`，便于存档或分享给同事套用。
- **导入参数**：读取 JSON 并套用。若源图尺寸或输出尺寸与记录不符，会降级套用并 toast 提示「效果仅供参考」，不做静默的错误恢复。

## 五、导出保存流程

### 5.1 完整链路

```
参数状态 (params)
   ↓  buildMatrix()         解算 3×3 齐次矩阵（输出像素 → 源图像素）
   ↓  renderTransformed()   逐像素反向映射 + 双线性采样 + 预乘 alpha 还原
   ↓  paintTo(ctx, w, h)    背景填充 → 前景合成（受 brightness/contrast 影响）
   ↓  applyDistort()        镜头畸变后处理（可选）
   ↓  exportCanvas()        产出目标尺寸的离屏 canvas
   ↓  download()            toBlob → 下载，PNG 时可选注入 tEXt 元数据
```

### 5.2 渲染三条硬规则

**① 反向映射，而非正向变换。**
遍历**输出**画布的每个像素，用矩阵求出它对应的**源图**坐标再采样。正向映射会产生空洞（源图某些像素映射到非整数位置，输出出现未赋值点），反向映射天然无空洞。

**② 双线性采样 + 预乘 alpha。**
直接对 RGBA 做加权平均，半透明边缘会混进黑色（因为透明像素的 RGB 是 0）。正确做法是先把 RGB 乘以 alpha 再加权，最后除以总权重还原，得到无色偏的边缘。

**③ 边界早退。**
源坐标超出 `[-1, w] × [-1, h]` 直接 `continue`，让该输出像素保持背景色——这正好实现了「旋转后边角露出背景」的自然效果。

### 5.3 导出产物

| 入口 | 产物 | 说明 |
|---|---|---|
| **下载当前照片** | 单张，PNG / JPG | 300dpi 印刷级尺寸，PNG 可注入参数元数据 |
| **下载排版图** | 6 寸 / 5 寸 / A4 拼版 | 自动计算行列数、裁切虚线，冲印店直接可用 |
| **一键下载三张** | 白 / 蓝 / 红底各一张 | 角度参数自动套用，无需重复调整 |

### 5.4 PNG 元数据

导出 PNG 时可选写入 `tEXt` 块（若用户取消勾选则跳过）：

```
关键字: IDPhotoStudio
内容:   { "app":"id-photo-studio", "kind":"id-photo-meta",
          "spec":{...}, "output":{...}, "background":{...},
          "transform":{...}, "angle":{"params":{...}} }
```

实现细节：直接操作 PNG 字节流，在 `IHDR` 之后插入合法 `tEXt` 块（自实现 CRC-32 校验），不依赖任何第三方库。改完的 Blob 仍然是完全合规的 PNG，任何看图软件都能正常打开。这为后续「把成品拖回工作台继续微调」留下了通道。

### 6.1 `transform.js` —— 几何变换引擎

**职责**：只做数学，不碰 DOM，不知道 UI 存在。

| 导出 | 作用 |
|---|---|
| `identity()` / `multiply()` / `mulVec()` | 3×3 齐次矩阵基础运算 |
| `perspectiveFrom4(dst, src)` | 由 4 组对应点解透视矩阵（高斯消元 + 列主元）。v1.2 起不在 `buildMatrix` 链上，保留作通用工具与射影性质测试 |
| `rotateDeg()` / `scaleXY()` / `translate()` | 基础 2D 变换 |
| `mirrorX(cx)` | 沿竖直线 x=cx 的镜像矩阵（对合，自身即逆） |
| `rotation3D(pitch, fov)` | 3D 俯仰旋转 + 透视投影 |
| `buildMatrix(params, ow, oh, sw, sh, pivot, view)` | **核心**：组装完整变换链 |
| `renderTransformed(ctx, src, m, ow, oh)` | 反向映射 + 双线性采样渲染 |
| `ANGLE_PARAMS` / `defaultParams()` / `isNeutral()` | 参数定义与中性判定 |

**矩阵组装顺序**（从外到内左乘，右结合意味着先施加右侧）：

```
M = cover · geo

geo = zoom · (fromNorm · R3D · toNorm) · rotate · mirror
                                        └── 内层：先翻照片 ──┘
```

**`mirror` 为什么放在最内层。** 矩阵链的方向是「输出 → 源图」，越靠右越先作用于取样。
把镜像放在最右，语义就是「先把源图翻个面，再做旋转/缩放」——
用户看到的是「照片内容被翻过来了」。如果放在外层，等价于「把已经排好的画面整体照镜子」，
在带旋转时会得到反直觉的结果（照片转了 30° 后翻面，看起来像往反方向转了 30°）。

**镜像的轴向固定在画布中线，不受 pivot 影响。** 镜像语义是「把这幅照片翻面」，
不是「绕某个点翻」。跟随 pivot 会让「换个旋转中心 → 照片突然左右跳到别处」。
测试 `镜像轴向不受旋转中心影响` 守住了这条。

拆开看每一步的意图：

1. `rotate` —— 最内层，画面内平面旋转；
2. `toNorm · ... · fromNorm` —— 把画布坐标归一化到 `[-1,1]`、做 3D 旋转投影、再还原回画布坐标；
3. `perspective` —— 输出矩形 → 源图梯形的映射；
4. `zoom` —— 最外层缩放，补偿上面几步造成的留白；
5. `cover` —— 最后套上源图的铺排矩阵。

> **踩坑记录**：初版把 `cover` 的居中基准也设成了 `pivot`，导致「换旋转中心 → 人像整体平移」。`cover` 必须恒定以画布中心为基准。

> **踩坑记录**：`rotation3D` 的投影矩阵最初写成 `[R0, R1, R2, R3, R4, R5, R6/d, R7/d, 1]`，导致非零旋转时边缘点坐标跑到 1.570（数值爆炸）。正确形式是第三列必须为 `0`，只有平移项和分母项参与投影：
> ```js
> return [R[0], R[1], 0, R[3], R[4], 0, R[6]/d, R[7]/d, 1];
> ```

### 6.2 `history.js` —— 历史栈

**职责**：通用的线性撤销/重做，不绑定任何业务概念。

- 构造参数：`{ limit, mergeMs, clone }`
- 核心方法：`reset` / `commit` / `seal` / `undo` / `redo` / `current` / `clear` / `list` / `on`
- 事件订阅：`status()` 返回 `{ canUndo, canRedo, size, index, label }`，UI 据此更新按钮禁用态。

因为不依赖 DOM、不依赖业务，这个类可以直接复用到涂抹笔刷、亮度对比度等其他需要撤销的功能上。

### 6.3 `angle.js` —— 角度控制器

**职责**：把参数、UI、交互、历史四者编排到一起。

与主应用的耦合通过 **依赖注入** 完成，避免循环依赖：

```js
new AngleController({
  getState:      () => S,           // 读共享状态
  getOutputSize: () => curPx(),     // 读当前输出尺寸
  onChange:      () => { ...重绘 }, // 参数变化时请求重绘
  toast:         (m) => toast(m),   // 显示提示
});
```

内部职责：

| 分组 | 方法 |
|---|---|
| 参数读写 | `getParams` / `setParams` / `isNeutral` |
| 矩阵与渲染 | `matrix` / `pivotPixel` / `renderForeground` / `applyDistort` |
| 历史 | `snapshot` / `initHistory` / `commit` / `seal` / `undo` / `redo` / `resetAll` / `resetCurrentGroup` / `resetPhoto` |
| 参数存档 | `exportParams` / `importParams` |
| UI 构建 | `_buildUI` / `_syncSliders` / `_syncModeUI` / `pivotModeUI` / `_syncHistoryUI` |
| 交互 | `beginDrag` / `drag` / `endDrag` / `nudge` / `_snap` |

### 6.4 `app.js` 的接入点

只改了四处，全部是**最小侵入**：

```js
// ① 渲染管线：角度启用时接管前景绘制
const handled = angle && angle.isEnabled() && angle.renderForeground(ctx, w, h);
if (!handled) ctx.drawImage(S.maskCanvas, t.dx, t.dy, t.dw, t.dh);

// ② 指针分发：新增 angle 模式分支
} else if (angle && angle.isEnabled()) {
  mode = 'angle';
  ...
}

// ③ 拖拽移动：把像素位移归一化后交给控制器
if (mode === 'angle') {
  angle.drag((e.clientX - last.px) / r.width, (e.clientY - last.py) / r.height);
}

// ④ 导出：畸变作为后处理
if (angle && angle.isEnabled() && !angle.isNeutral() && angle.params.distort) {
  angle.applyDistort(ctx, p.w, p.h);
}
```

`angle.enabled = false` 是默认值——不开启时 `renderForeground` 直接返回 `false`，主流程走原来的 `drawImage` 路径，性能与行为完全不变。

## 八、性能与精度

### 8.1 性能

| 环节 | 量级 | 说明 |
|---|---|---|
| `buildMatrix` | < 0.01ms | 9 次矩阵乘法 |
| `renderTransformed` | 300×400 画布 ≈ 15ms | 逐像素反向映射，最重的一环 |
| 拖拽重绘 | ~60fps 可用 | 只在参数变化时重算，不做无谓重建 |
| 遮罩重建 | 不触发 | 角度调整只重绘，不重新抠图 |

**关键优化决策**：角度变化**不重建抠图遮罩**。`onChange` 回调里只做 `paintTo` + `drawGuides`，避开了最耗时的分割推理，这是拖拽能做到跟手的原因。

### 8.2 精度

- 矩阵用双精度浮点，`isIdentityMatrix` 判等阈值 `1e-9`，`isNeutral` 阈值 `1e-6`。
- 采样用双线性插值，优于最近邻（无锯齿）且快于双三次（移动端可接受）。
- 旋转 45° 的斜边会有轻微软边，这是重采样的固有代价，属正常范围。

### 8.3 已知限制

| 限制 | 说明 | 缓解 |
|---|---|---|
| 旋转超过 ±25° 边缘模糊 | 3D 投影拉伸放大像素 | 提示用户尽量重拍 |
| 透视校正不改变光照 | 只做几何矫正，侧面拍的高光阴影仍在 | 不属于本功能职责 |
| 旋转后边角露背景 | 反向映射的自然结果 | `zoom` 参数可放大补偿 |
| 不生成缺失像素 | 极端角度下脸部大面积缺失无法补全 | 明确的能力边界，不假装能做 |

## 十一、端到端实测发现与修正（v1.1）

单元测试全绿不等于功能可用。用真实浏览器 + 真实 MediaPipe 模型跑完整流程后，暴露出 6 个单测覆盖不到的缺陷——**其中 4 个是功能性 bug，2 个是测试方法本身的错误**。

### 11.1 功能性缺陷

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| B1 | 开启角度模式后，自动构图失效、人像跑偏 | `buildMatrix` 的 `cover` 硬编码居中铺满，完全忽略主应用的 `S.tf`（scale/nx/ny） | `buildMatrix` 增加 `view` 参数承接构图状态，`AngleController.matrix()` 传入 `st.tf` |
| B2 | 复位后画面与初始不一致 | 中性参数时 `renderForeground` 返回 `false`，走 `drawImage` 路径；一旦动了参数就切到矩阵路径，两条路径产出不一致 | 角度模式开启即**始终接管**渲染，消除路径切换 |
| B3 | 纵向透视无效果，只表现为整体缩放 | `srcQuad` 里 `leftK` 同时作用于顶边两点 → 顶边整体上下移动，不是梯形 | 四顶点独立控制：顶边两点 x 由 `perspX` 决定，左右两点 y 区间由 `perspY` 决定 |
| B4 | 透视方向与语义相反（要做成上宽下窄） | 矩阵是「输出→源图」，`1 - px` 使顶部取样更窄 ⇒ 顶部被放大 | 改为 `1 + px`，取样更宽 ⇒ 视觉收窄，与文档语义一致 |
| B5 | 数值输入框不遵守水平吸附，与滑块行为不一致 | 数值输入通道漏调 `_snap()` | 补上 `_snap()` 并回写吸附后的值 |
| B6 | 方向键微调永远调不动 | 微调步长 1° 落在 ±2° 吸附区内，一按就被吸回 0 | 微调**不做吸附**（吸附语义是「靠近水平帮你归零」，微调语义是「我要精确控制」），并加 `roundTo()` 消除浮点噪声 |
| B7 | 旋转中心「点了没反应」，且每次旋转都被悄悄改掉轴心 | ① `pivotXY` 赋值后不触发重绘；② `pointerdown` 里无条件按点击位置设轴心 | ① 改为拖拽轴心标记才移动轴心，`hitPivot()` 判定命中；② 移动后立即重绘；③ 轴心标记放大到 `max(10, w*0.075)` 并加文字标签 |
| B8 | 构图辅助线开启后，角度网格与轴心标记整个消失 | `drawGuides` 写成 `if (!S.guides) { drawAngleOverlay(); return; }` | `drawAngleOverlay` 改为**无条件调用** |

> B1 与 B2 是同一个思维陷阱的两面：**「新渲染路径」必须与「已有渲染路径」在几何上等价**，否则开关一切换就会跳变。

### 11.2 测试方法本身的错误（值得单独记录）

端到端测试写错判据，会制造假失败、掩盖真问题。本轮踩到 4 个：

| 错误判据 | 问题 | 正确做法 |
|---|---|---|
| 用「像素与背景色不同」判断前景占比 | 白底 + 白背景时整幅都是白的，判定必然失效 | 直接读 `maskCanvas` 的 alpha 通道统计 |
| 用逐像素哈希判断「画面是否复原」 | `drawImage` 与自实现采样器的插值算法不同，**同样的几何**也会产生不同像素值 | 改用**结构指标**：前景 bbox + 质心（实测差 0.1px 即通过） |
| 用「质心位移」判断旋转中心是否生效 | 人像近似对称时，绕不同轴心旋转后质心几乎不动 | 用 bbox 差 + 面积差综合判断 |
| 用「左右两列的 y 跨度对比」判断纵向透视 | **射影变换保持对边比**，两条对边的跨度恒等，该指标在数学上永真 | 看左右顶点 y 是否错开（真正的梯形特征） |

> 教训：**判据必须建立在数学性质上，而不是「看起来应该不同」的直觉上**。射影几何下对边比不变、插值实现差异、对称图形的质心不变性，都是会骗人的。

## 十二、v1.2 参数精简记录

### 12.1 为什么砍

原 9 参数版本把「几何上能做」当成了「产品上该做」。实盘用下来有两条硬伤：

1. **概念密度过高。** 普通用户分不清「水平旋转」和「倾斜（Roll）」的区别 —— 两者在
   证件照语境下都表现为「把人转正」。Roll 只是绕视线轴、Rotate 是整幅画面在平面内转，
   在纯 2D 校正场景里结果高度重合，留两个入口是纯负担。
2. **透视校正缺少适用场景。** `perspX` / `perspY` 是为「斜拍证件」设计的，但证件照工作台
   的输入永远是**人像照**，人像是软的、没有可对齐的直线边，用户看不出梯形该往哪个方向矫。
   参数留下了，认知成本留下了，收益几乎为零。

`yaw`（转头）同理：纠正侧脸需要生成不存在的像素（见 §1.2 设计边界第一条），
它做的只是把侧脸投影拉伸，效果不像「纠正」更像「变形」，容易被误用。

### 12.2 砍掉了什么

| 参数 | UI 名称 | 处理 |
|---|---|---|
| `roll` | 倾斜（Roll） | **移除**。需求由 `rotate` 承接 |
| `yaw` | 转头（Yaw） | **移除**。违反「不生成不存在像素」的设计边界 |
| `perspX` | 横向透视 | **移除**。人像照无可对齐的直线边，无适用场景 |
| `perspY` | 纵向透视 | **移除**。同上 |

保留 5 项：`rotate` / `pitch` / `zoom` / `distort` / `fov`。

### 12.3 代码怎么改

关键点：**`ANGLE_PARAMS` 是唯一事实来源。** 滑块、`defaultParams()`、`isNeutral()`、
导出 JSON 全部由这个数组驱动，所以「删参数」的主改动只有一处 —— 从数组里去掉 4 项。
其余需要跟着动手的地方是那些写死了具体参数的逻辑：

| 位置 | 改动 |
|---|---|
| `transform.js` `rotation3D(pitch, yaw, roll, fov)` | 签名收缩为 `rotation3D(pitch, fov)`，旋转矩阵退化为单轴 `Rx` |
| `transform.js` `buildMatrix` | 删掉整个透视梯形分支；`has3D` 判据由 `pitch \|\| yaw \|\| roll` 改为 `!!pitch` |
| `transform.js` `perspectiveFrom4` | **保留**（不再是主链一环），留作通用四点矫正工具 + 射影性质测试载体 |
| `angle.js` `GROUPS` | 只留 `rotate` / `pitch` 两组 |
| `angle.js` `_snap` | 吸附判据由 `rotate \|\| roll` 收缩为 `rotate` |
| `angle.js` `drag` | `SENS` 收缩为 `{ rotate, pitch }`，删 3 个 case |
| `angle.js` `nudge` / `endDrag` | 去掉 `this.mode === 'persp' ? 'perspX' : this.mode` 这类特判 |
| `index.html` | 快捷模式按钮由 5 个减为 2 个 |

### 12.4 测试怎么改

删掉参数的测试不能简单删除，要**改成反向断言**，否则将来有人手滑加回来不会有人发现：

```js
// _test.mjs
for (const key of ['roll', 'yaw', 'perspX', 'perspY']) {
  const pp = { ...p0, [key]: key.startsWith('persp') ? 0.3 : 20 };
  const Mp = buildMatrix(pp, 295, 413, 1200, 1600);
  // 已移除的参数即使被赋值，也必须对矩阵零影响
  t(`${key} 已移除，不再影响矩阵`, diff(Mp, M0) < 1e-9);
}
```

```js
// _e2e/run.mjs —— 同时验证「面板上没有」和「快捷模式里没有」
for (const key of ['roll', 'yaw', 'perspX', 'perspY']) {
  const n = await page.locator(`.angle-num[data-key="${key}"]`).count();
  n === 0 ? ok(`${key} 已从面板移除`) : bad(`${key} 仍存在于面板`);
}
for (const m of ['roll', 'yaw', 'persp']) {
  const n = await page.locator(`#angleMode button[data-m="${m}"]`).count();
  n === 0 ? ok(`快捷模式「${m}」已移除`) : bad(`快捷模式 ${m} 仍存在`);
}
```

导出 JSON 也加了一条：`导出的 JSON 不应再含有已移除的字段`，防止旧存档字段被静默带出。

### 12.5 顺带修掉的两个测试自身的错误

改测试时发现原来的断言本身就不对：

1. **`distort 参数生效`** —— 拿 `buildMatrix` 的返回值比差异，但 `distort` 根本不在矩阵链上，
   它是渲染阶段的逐像素径向函数（`distortFactor`）。矩阵必然零差异。
   改为断言「`distort` **不**改变矩阵」。
2. **`fov 参数生效`** —— `fov` 只在 `pitch ≠ 0` 时才进入矩阵，中性参数下测必然失败。
   改为固定 `pitch: 15`，比较 `fov: 1.0` 与 `fov: 3.0` 的矩阵差异。

这两条说明一个通用教训：**断言要写在参数真正生效的那一层**。参数分成「进矩阵的」和
「走渲染的」两类，混在一张表里跑同一个判据，必然误报。

## 十三、v1.3 能力补强记录

### 13.1 自由旋转：±45° → ±90°

原上限 45° 是按 v1.0 的假设定的 —— 那时认为「超出 45° 的歪斜照片本身已不适合做证件照」。
但实际使用中出现了一类没被考虑到的输入：**横竖方向颠倒的照片**。

- 手机横着拍的竖构图人像；
- 扫描仪 / 翻拍时方向搞反的证件素材；
- 用户希望把照片转 90° 后重新构图。

这类需求下 45° 根本不够用，用户只能先去别的工具转正再回来。放开到 90° 直接覆盖。

**为什么不干脆开到 ±180°。** 90° 是个天然的对称点：左右边界互为镜像，且不存在
「转过去一点」的中间态。超过 90° 的部分与 `镜像 + 反向旋转` 等价 ——
用户可以自己拼出来（镜像 + 90° 就是 270°，镜像 + 45° 就是 135°），
单设 180° 量程只是把同一批结果重复暴露一次，还让滑块中位难以回到 0°。

**配套调整：拖拽灵敏度 42 → 60。** 量程翻倍后若沿用原灵敏度，拖满一次画布
只能覆盖不到一半量程，用户得拖两三次才到端点。60 的含义是「拖满约 1.5 个画布宽
可达端点」—— 小幅摆正仍在一拖之内，大角度翻转也不必反复拖。

### 13.2 镜像：新增布尔开关

**`mirror` 为什么单独列成 `ANGLE_FLAGS`。** 它没有 `min` / `max` / `step`，
所有「参数表驱动滑块渲染」的逻辑都套不上。硬塞进 `ANGLE_PARAMS` 会让
`_buildUI` 里到处是 `if (p.isFlag)` 的特判。拆成两张表后，两边各自干净：

```js
export const ANGLE_PARAMS = [ /* 数值参数，走滑块 + 数值输入 */ ];
export const ANGLE_FLAGS  = [ /* 布尔开关，走 checkbox */ ];

export function defaultParams() {
  const o = {};
  for (const p of ANGLE_PARAMS) o[p.key] = p.def;
  for (const f of ANGLE_FLAGS) o[f.key] = f.def;   // 别漏了这行
  return o;
}
```

`isNeutral()` 同样要遍历两张表，否则「只勾了镜像」会被判成中性，
渲染路径可能提前退回 `drawImage` 而忽略镜像。单元测试
`mirror=true 时非中性` 专门守这条。

**`mirrorX(cx)` 的实现与对合性。** 沿竖直线 `x = cx` 的镜像矩阵：

```js
export function mirrorX(cx) {
  return [-1, 0, 2 * cx, 0, 1, 0, 0, 0, 1];
}
```

即 `x' = 2cx − x`，`y' = y`。翻转是对合运算（自己的逆就是自己），
所以同一个矩阵既表达正向翻转、也表达反向翻转 —— 本项目的矩阵链是
「输出 → 源图」的反向映射，这里刚好不需要取逆。测试
`镜像是对合的（翻两次回到原位）` 用 `M · M = I` 验证。

**轴向为什么固定在画布中线。** 镜像的语义是「把这幅照片翻个面」，
不是「绕某个点翻面」。如果让它跟随 `pivot`，用户每换一次旋转中心，
照片就会突然左右跳到别处。端到端用例
`镜像轴向不受旋转中心影响` 对两个极端 pivot 求矩阵差，要求严格为 0。

**镜像在矩阵链中的位置：最内层。** 见第六章的链路图。放在最右意味着
「先翻源图，再旋转 / 缩放」。若放在外层，等价于「把已排好的画面整体照镜子」，
在带旋转时结果反直觉（转了 30° 再翻面，看起来像往反方向转了 30°）。
端到端与单元测试各有一条守住这个语义。

### 13.3 测试增量（104 → 133 项）

新增 29 项：单元 10 项（镜像性质 + 量程断言），端到端 19 项（量程放开、
拖拽突破 45°、90° 下画面有效、镜像的对称性 / 对合性 / 可撤销性、
镜像与旋转的组合渲染、复位后回到关闭、导出 JSON 含 `mirror` 字段等）。

单元测试 `[6d] 镜像` 覆盖：

| 断言 | 守护的性质 |
|---|---|
| 默认 mirror = false | 默认值 |
| `mirror=true` 时非中性 | `isNeutral` 遍历两张表 |
| 镜像把左边界映射到右边界 | `x → 2cx − x` 正确 |
| 镜像不改变 y | 只翻水平方向 |
| 镜像保持画布中心不动 | 轴向在中线 |
| 镜像是对合的 | `M·M = I` |
| 镜像先于旋转生效 | 矩阵链中的位置正确 |
| 镜像轴向不受旋转中心影响 | 与 pivot 解耦 |

单元测试 `[6]` 补充：`自由旋转范围 ±90°`。

### 13.4 一个被顺手排除的担心

量程放到 90° 时，第一反应是「转这么多角，输出画布四角会不会转出源图范围、露出空白」——
毕竟 `cover` 只保证 0° 时铺满。

实测结论：**不会**。`_e2e/rot90_shot.mjs` 在 0° / 45° / 90° / 90°+镜像 四个状态下
采样输出画布四角 alpha，全部为 255（不透明）：

```
rotate=0     四角 alpha: 255 255 255 255 → 满幅
rotate=45    四角 alpha: 255 255 255 255 → 满幅
rotate=90    四角 alpha: 255 255 255 255 → 满幅
rot90+mirror 四角 alpha: 255 255 255 255 → 满幅
```

原因是源图（1200×1600）相对输出画布（295×413）有大量余量，`cover` 的放大倍数
足以吸收 90° 内的旋转位移。但**这不代表所有源图都安全**：若源图本身接近
输出画布的宽高比（余量小），大角度旋转仍可能露角。用户可自行用 `zoom` 补偿 ——
这也是「画面缩放」参数保留至今的原因。

## 十四、v1.4 弱网可用性修复记录

### 14.1 现象

用户在浏览器里看到界面**永久停在「正在准备模型…」**，图片读不出来。
本地复现时流程正常（`initMatting` 256ms 完成），说明不是逻辑 bug。

### 14.2 根因定位

用 Python 直接测线上资源的实际吞吐：

| 环境 | 压缩前 | Content-Encoding | 实收 | 耗时 | 速率 |
|---|---|---|---|---|---|
| 本地 127.0.0.1 | 9.4 MB | — | 9,423,986 B | 0.1 s | 极快 |
| GitHub Pages（国内） | 9.4 MB | gzip | 2,903,515 B | **68.1 s** | **≈43 KB/s** |

两处结论：

1. **GitHub Pages 已自动 gzip**，9.4 MB → 2.9 MB（压掉 69%），无需自己压。
2. **瓶颈是带宽不是体积**。2.9 MB 在 43 KB/s 下要 68 秒，加上 bundle（137 KB）
   和两个 tflite（480 KB），首屏完整加载接近 **1.5–2 分钟**。

而界面在这 1–2 分钟里**只有一行静态文案**，没有百分比、没有超时、没有重试 ——
用户无法区分「正在下载」和「已经卡死」，这是体验问题的根源。

### 14.3 修复内容

**a) 下载进度可观测**

`matting.js` 新增 `setProgressHandler(fn)`，初始化过程广播四个阶段：

| 阶段 | 触发时机 | UI 文案 |
|---|---|---|
| `prefetch` | 开始探测 wasm | 正在准备模型… |
| `download` | 流式读取中，每次 chunk | 正在下载模型 42%（4.0/9.4 MB · 77 KB/s） |
| `parsing` | 交给 MediaPipe 解析 | 正在解析模型… |
| `ready` | 完成 | 遮罩关闭 |

进度通过 `fetch` + `ReadableStream.getReader()` 逐块统计。**不落地 blob** ——
因为 MediaPipe 的 `FilesetResolver` 无法复用外部 blob，落地只会白占内存
（实测会使 wasm 被请求 3 次而非 2 次）。探测请求带 `cache: 'force-cache'`，
反而让后续 MediaPipe 的请求命中缓存。

**b) 卡顿看门狗**

8 秒内进度无变化 → 在文案下追加「网络较慢，请耐心等待，勿关闭页面」。
只提示、不中断，避免误杀慢速但正常的下载。

**c) 失败不再永久锁死**

原实现 `initPromise` 一旦 reject 就永久缓存坏状态，用户只能刷新页面。
现在：

```js
initPromise.catch((e) => {
  lastError = String((e && e.message) || e);
  if (!force) initPromise = null;   // 清掉坏缓存，允许重试
});
```

`initMatting(force)` 传 `true` 时清空 `segmenter` / `faceDetector` / `lastError`
重新走一遍。

**d) 重试入口**

遮罩内新增 `#loadRetry` 按钮。点击后按三档分支处理，**任何分支都不会把用户
锁在遮罩里**：

1. 模型就绪 + 有原图 → 重跑完整抠图流程（文案显示「模型已就绪，正在重新抠图…」）
2. 模型就绪但无原图 → 关闭遮罩
3. 模型仍不可用但已有抠图结果 → 关闭遮罩，提示可用纯色抠图或手工修边
4. 完全无结果 → 保持失败态，允许再次重试

### 14.4 本地开发服务器

排查过程中踩到一个假故障：`python -m http.server` 会发 `Last-Modified`，
浏览器据此**启发式缓存** JS 文件。改了 `matting.js` 新增导出后，页面仍执行旧版，
报：

```
The requested module './matting.js' does not provide an export named 'initError'
```

整个页面 JS 因此挂掉，表现和「模型卡住」一模一样。新增 `_serve.py`，在
`end_headers()` 里强制 `Cache-Control: no-store`，并在启动 bat 中改用它。

### 14.5 未采纳的方案

| 方案 | 为何不采纳 |
|---|---|
| 换 Cloudflare / 其他 CDN 托管 wasm | 用户网络环境屏蔽 `workers.dev` / `pages.dev`，不可靠 |
| 自己 gzip 后上传 | GitHub Pages 已自动 gzip，手动压无收益 |
| 给 wasm 加 Service Worker 预缓存 | 首次访问仍要下 2.9 MB，收益只在二次访问；浏览器 HTTP 缓存已覆盖 |
| 缩小 wasm | MediaPipe 官方产物，无裁剪手段 |

**结论**：纯前端能给的最好体验就是「让等待可见」。带宽问题需换托管才能根治。

### 14.6 测试补充

| 用例 | 断言 |
|---|---|
| 加载遮罩含重试按钮 | `#loadRetry` 存在 |
| 重试按钮默认隐藏 | 初始 `hidden` |
| 初始化触发 ready 事件 | 强制 `force=true` 重跑，事件序列含 `prefetch → … → parsing → ready` |
| 可进入失败态 | 切换后遮罩与按钮同时可见 |
| 点重试后恢复 | 轮询至遮罩关闭 |
| 无坏缓存 | 连续两次 `initMatting(false)` 结果一致 |

**踩坑**：断言 `ready` 事件时必须用 `force=true`。首次加载已完成初始化，
`initPromise` 已缓存，再调 `initMatting(false)` 会直接返回缓存结果、不发任何事件。

### 14.7 踩坑记录

**Playwright `waitForFunction` 参数位置**

```js
// ✗ 错误：{timeout} 被当成 arg 传入，超时仍是默认 30s
await page.waitForFunction(fn, { timeout: 90000 });

// ✓ 正确：签名是 (pageFunction, arg, options)
await page.waitForFunction(fn, null, { timeout: 90000 });
```

症状极具误导性：报错写 `Timeout 30000ms exceeded`，而代码里明明写了 90000。

**`page.click` 在切过 tab 后可能静默不触发**

切到导出 tab 后遮罩位于舞台区，`page.click('#loadRetry')` 的可见性校验通过、
`elementFromPoint` 也确认命中按钮，但 handler 未执行。改用原生派发：

```js
await page.evaluate(() => document.querySelector('#loadRetry').click());
```

**固定 profile 会缓存旧版 JS**

`rot90_shot.mjs` 原用固定 profile `pw-render/rot90`，反复跑会命中内存/HTTP 缓存
中的旧模块。改为 `rot90-${Date.now()}`，每次全新。

### 14.8 线上冒烟发现的进度 bug（gzip 与 content-length）

推送后用 `_e2e/online_smoke.mjs` 在**真实网络**下跑了一遍线上站点，抓到一处
本地测不出来的错误：

```
「正在下载模型 99%（8.9/2.8 MB · 1549 KB/s）」
```

**`got` 超过了 `total`，百分比卡死在 99%。**

**原因**：线上走 gzip，`Content-Length` 是**压缩后**大小（2,903,515 B），
而 `fetch` + `getReader()` 读出来的是**解压后**数据（9,423,986 B）。
两者不同量纲，相除必然越界。本地服务器不压缩，所以本地永远复现不出来。

**修复**：以 wasm 解压后的真实字节数为基准，取两者较大值兜底。

```js
const WASM_DECODED_SIZE = 9423986; // vendor/wasm/vision_wasm_internal.wasm 解压后大小
const cl = Number(res.headers.get('content-length')) || 0;
const total = cl >= WASM_DECODED_SIZE ? cl : WASM_DECODED_SIZE;
```

**回归测试**：E2E 里用 `page.route` 伪造压缩头，断言 `total` 仍取解压体积：

```js
await page.route('**/vision_wasm_internal.wasm', async (route) => {
  const resp = await route.fetch();
  const body = await resp.body();
  await route.fulfill({ body, headers: { ...resp.headers(), 'content-length': '2903515' } });
});
// 断言 total === 9423986（而不是 2903515）
```

**教训**：凡是把「网络层字节数」和「应用层字节数」放一起做算术，都要先确认两者
是否同一量纲。压缩传输下 `content-length` 是前者。

### 14.9 Playwright API 参数个数要逐个确认

`waitForFunction` 和 `waitForSelector` 的签名**不一样**，照搬会报错或静默用错超时：

```js
// waitForFunction(pageFunction, arg, options) —— 三参
await page.waitForFunction(fn, null, { timeout: 90000 });

// waitForSelector(selector, options) —— 两参，多传一个 null 会崩
await page.waitForSelector('#drop', { timeout: 120000 });
```

两参版本传成三参的真实报错：

```
TypeError: Cannot read properties of null (reading 'visibility')
  at _Frame.waitForSelector (coreBundle.js:60023:21)
```

## 十五、v1.5 调色 × 角度一致性修复

### 15.1 现象

> 「我本身的照片比较糊，我调了对比度变清晰了，但是一调角度又糊了。」

用户用**提高对比度**来补偿原图的模糊感，效果满意；但只要进入角度模式，
画面立刻发灰、又「糊」回去。

### 15.2 根因

渲染有**两条路径**：

| 路径 | 触发条件 | 实现 |
|---|---|---|
| A | 未开角度 | `ctx.drawImage(src, dx, dy, dw, dh)` —— 浏览器原生高质量缩放 |
| B | 开了角度 | `renderForeground` → `renderTransformed` —— **手写逐像素双线性采样**，最后 `putImageData` 写回 |

而亮度/对比度当时是靠 `ctx.filter` 实现的，设在调用渲染之前：

```js
if (S.bri !== 100 || S.con !== 100) ctx.filter = `brightness(${S.bri}%) contrast(${S.con}%)`;
const handled = angle && angle.isEnabled() && angle.renderForeground(ctx, w, h);
if (!handled) ctx.drawImage(S.maskCanvas, t.dx, t.dy, t.dw, t.dh);
```

**`ctx.filter` 只对绘制操作（drawImage / fillRect 等）生效，对 `getImageData` /
`putImageData` 完全无效**（这是 Canvas 规范行为）。路径 B 内部正是
`getImageData` 读背景 → 逐像素合成 → `putImageData` 写回，滤镜被整段绕过。

### 15.4 修复：把调色预烘焙进源画布

不再依赖运行时的 `ctx.filter`，改为在调色参数变化时**把亮度/对比度烘进像素**，
两条路径共用同一张已调色的画布：

```js
function buildEnhanced() {
  if (!S.maskCanvas) { S.enhanced = null; return; }
  if (S.bri === 100 && S.con === 100) { S.enhanced = S.maskCanvas; return; } // 默认值不拷贝
  if (!S.enhancedCanvas) S.enhancedCanvas = document.createElement('canvas');
  S.enhancedCanvas.width = S.W;
  S.enhancedCanvas.height = S.H;
  const c = S.enhancedCanvas.getContext('2d');
  c.clearRect(0, 0, S.W, S.H);
  c.filter = `brightness(${S.bri}%) contrast(${S.con}%)`; // 作用于 drawImage，落进像素
  c.drawImage(S.maskCanvas, 0, 0);
  c.filter = 'none';
  S.enhanced = S.enhancedCanvas;
}
```

改动点：

- `S` 新增 `enhanced` / `enhancedCanvas`
- `buildMask()` 末尾调用 `buildEnhanced()`
- `paintTo` 用 `S.enhanced` 绘制，**删除** `ctx.filter` 那行
- `renderForeground` 读 `st.enhanced || st.maskCanvas`
- `#bri` / `#con` 的 `oninput` 增加 `buildEnhanced()`
- 「重做」清理时一并置空

**收益**：调色参数默认时零拷贝；非默认时只烘焙一次，之后每帧（拖拽、旋转）
都直接复用，反而比每帧套滤镜更快。

### 15.7 通用教训

**同一份视觉结果若有多条渲染路径，任何「运行时依赖上下文状态」的效果
（滤镜、混合模式、变换）都必须确认在每条路径上都成立。**

本次的 `ctx.filter` + `putImageData` 组合是典型的「A 路径好用、B 路径静默失效」——
不报错、不警告，只是效果消失，靠肉眼对比才发现。

**更稳的做法**：把这类效果**烘焙进像素**（预先算出中间画布），
而不是依赖绘制时的上下文状态。既消除路径差异，又顺带省掉每帧的重复计算。

### 15.8 诊断方法：用像素统计替代肉眼

肉眼判断「糊」很主观且容易归因错误。用可量化指标：

- **对比度** → 不透明像素亮度标准差 `sd`
- **锐度** → 相邻像素亮度梯度均值

```js
// 只统计不透明像素，避免背景干扰
for (let i = 0; i < d.length; i += 4) {
  if (d[i + 3] < 250) continue;
  const y = 0.299 * d[i] + 0.587 * d[i + 1] + 0.114 * d[i + 2];
  sum += y; sum2 += y * y; n++;
}
const mean = sum / n;
const sd = Math.sqrt(sum2 / n - mean * mean);
```

再配合一个**对照组**（同一张图、同样参数，只切换渲染路径），
差异就能被稳定复现和断言，而不是靠感觉。
